# Architecture

Student Dues Payment SaaS — multi-tenant platform for educational organizations to configure dues, accept payments, distribute funds between faculty/department, and maintain financial and audit records.

This document is the durable reference for decisions made in Phase 0. It is expected to be extended (not replaced) as later phases add models, services, and features.

## Next.js version notes

This project runs Next.js 16.3.4, which has real breaking changes from older versions. Before writing framework-facing code, consult `node_modules/next/dist/docs/` — do not assume older Next.js conventions apply. Notably:

- `middleware.ts` is deprecated and renamed to **`proxy.ts`** (`proxy()` export, not `middleware()`).
- **Cache Components** (`"use cache"`, `cacheComponents: true`) are opt-in and **intentionally disabled** in this project (see `next.config.ts`). This app is almost entirely authenticated, tenant-scoped, real-money data with no static/marketing surface — the PPR/Suspense discipline Cache Components require buys nothing here and adds real risk of caching one tenant's financial data where another could see it. All authenticated routes render dynamically per request.
- `params`/`searchParams` are `Promise`s; use the auto-generated `LayoutProps<'/path'>`, `PageProps<'/path'>`, `RouteContext<'/path'>` helpers instead of hand-written param types.

## Application architecture

`src/` layout, App Router, route groups per audience so layouts differ without affecting the URL:

```
src/
├── app/
│   ├── (auth)/                     # /login — public, unauthenticated
│   ├── (platform)/super-admin/     # Super Admin console
│   ├── (org)/admin/                # Organization Admin
│   ├── (org)/faculty/[facultyId]/  # Faculty Dean/President/Treasurer
│   ├── (org)/department/[deptId]/  # HOD/President/Treasurer
│   ├── (org)/pay/[orgSlug]/        # Public student payment flow (by index number)
│   ├── student/                    # Student receipt/history lookup
│   └── api/webhooks/hubtel/route.ts
├── components/{ui,dashboard,finance,payments,tables,forms,charts}/
├── lib/{auth,db,permissions,payments,finance,audit,notifications,reports,validation}/
├── models/       # Mongoose schemas
├── services/     # orchestration over models + lib
├── types/
├── hooks/
└── utils/
proxy.ts          # repo root, optimistic auth redirect only
```

Route groups are an organizational convenience only. **Scope enforcement (an org admin can't see another org, a faculty exec can't see another faculty, etc.) is never trusted from the URL** — it happens in the DAL/services layer on every read and write. See `src/lib/permissions/`.

## Database architecture

- MongoDB + Mongoose, single cluster, **shared multi-tenant collections**. Every tenant-owned document carries `organizationId` (and `facultyId`/`departmentId` where applicable), indexed, compared against the session's scope before any query runs.
- Financial state transitions (payment confirmed → ledger entries → faculty/department balance split) use Mongoose **multi-document transactions** so a payment is never marked successful without its ledger entries being written atomically.
- `src/lib/db/connection.ts`: `globalThis`-cached connection singleton, safe across Next.js dev-mode hot reloads.

## Authentication & session architecture

Custom, DAL-based — not a third-party auth library — because the 8-level scoped role hierarchy doesn't map cleanly onto a generic library's session model.

- Passwords: bcrypt (`src/lib/auth/password.ts`).
- Session: JWT signed with `jose` (HS256), minimal payload (`userId`, `role`, `organizationId?`, `facultyId?`, `departmentId?`, `expiresAt`) — no PII (`src/lib/auth/session.ts`). Stored in an `httpOnly`, `secure`, `sameSite=lax` cookie.
- `src/lib/auth/dal.ts`: `getSession()` / `verifySession()`, wrapped in React's `cache()` — the single source of truth, called from every page, Server Action, and Route Handler that touches data. A layout-level check alone is not sufficient (layouts don't re-run on client-side navigation), and Server Actions are not covered by a proxy matcher change, so every mutation re-verifies.
- `proxy.ts`: optimistic redirect only (unauthenticated → `/login`, authenticated hitting `/login` → dashboard). Reads the cookie, does not hit the database, and is never the actual security boundary.

## RBAC & tenant isolation

Roles (`src/lib/permissions/roles.ts`): `SUPER_ADMIN`, `ORG_ADMIN`, `FACULTY_DEAN`, `FACULTY_PRESIDENT`, `FACULTY_TREASURER`, `DEPT_HOD`, `DEPT_PRESIDENT`, `DEPT_TREASURER`, `STUDENT`.

- `src/lib/permissions/scope.ts`: structural guards (`inOrganization`, `inFaculty`, `inDepartment`) comparing a resource's own scope fields against the session's scope — this is what actually stops cross-tenant access.
- `src/lib/permissions/can.ts`: capability-based checks (`can(user, 'withdrawal:approve', { departmentId })`) so a permission's scope rule is defined once and reused everywhere, instead of `role === 'x'` checks scattered through pages.
- Every service function that reads or writes tenant data takes the authenticated session and asserts scope membership before querying.

## Payment gateway architecture (Hubtel)

- `src/lib/payments/provider.ts`: a `PaymentProvider` interface (`initiate`, `verify`, `parseWebhook`) so Hubtel is a swappable implementation.
- Hubtel (Receive Money / Checkout — MTN MoMo, Vodafone Cash, AirtelTigo, cards) is the first and only implementation. Flow: student looks up dues by **index number** → initiates payment → Hubtel calls `app/api/webhooks/hubtel/route.ts` → the handler verifies the transaction status server-side (a webhook payload is authenticated, never trusted on receipt alone) → on confirmed success, a DB transaction atomically marks the payment successful, writes ledger entries, and applies the faculty/department split. **Receipts are generated only after this confirmed state**, never speculatively.
- Hubtel credentials live in env vars, read only inside `src/lib/payments/hubtel.ts` (Phase 1+).

## Audit architecture

Single `recordAudit(actorId, action, target, metadata)` helper (`src/lib/audit/`, Phase 1+). Every mutating service call is expected to call it — audit logging is a service-layer responsibility, not bolted on in the UI.

## Notification architecture

Provider-agnostic email/SMS interface (`src/lib/notifications/`, Phase 1+), consumed by payment confirmation, withdrawal approval, and student-list-match flows.

## File upload architecture

Official student list imports go through Route Handlers using `Request.formData()`, parsed server-side, matched against payment records by index number (Phase 2+, once the Student model exists).

## Reporting architecture

Query-builder helpers under `src/lib/reports/` built out once ledger/payment models exist (Phase 2+): reconciliation reports, ledger exports, per-faculty/department balances.

## Design system

Tailwind v4, CSS-first `@theme` tokens (`src/app/globals.css`) — a deliberate fintech palette (ink/navy neutrals, one restrained teal accent, semantic success/pending/danger colors), not a purple/blue gradient template look. UI primitives (`src/components/ui/`) are hand-built on Radix primitives + `class-variance-authority` + a `cn()` helper (`src/utils/cn.ts`), not a stock component-library skin.

## Phase 1: Database

All 29 collections from the product spec are implemented under `src/models/`, one file per model, sharing two fragments from `src/models/shared/`: `auditFieldsSchemaDefinition` (`createdById`/`updatedById`, nullable for system/webhook writes — `createdAt`/`updatedAt` come from Mongoose's `{ timestamps: true }`) and `deactivationFieldsSchemaDefinition` (`isActive`/`deactivatedAt`/`deactivatedById`). Every model uses the `models.X ?? model<X>(...)` guard to survive Next.js dev hot-reload without `OverwriteModelError`.

**Money and percentages are always integers.** Amounts are `amountPesewas` (integer minor units); revenue splits are integer basis points (10000 = 100%), validated by a schema-level check on `RevenueAllocationRule.splits`. No float currency math anywhere in the schema layer.

**RBAC is normalized: `Role` (catalog) + `UserRole` (assignment) + `User` (credentials only).** `User` carries no role or scope fields — a `UserRole` row assigns one `Role` to one user within a scope (`organizationId`/`facultyId`/`departmentId`, as required by that role's level). A partial unique index on `UserRole` (`{ userId }`, filtered to `isActive: true`) allows at most one active assignment per user, so login stays a single lookup while full role-change history is preserved (old rows are deactivated, never deleted or overwritten). `Role` is seeded from the `ROLES` enum in `src/lib/permissions/roles.ts`, which remains the source of truth for TypeScript types and the `can()`/scope rules — the DB catalog exists for referential integrity and Super Admin visibility, not to replace the code-level rules.

**Students are roster rows, not accounts.** `Student` holds no password — the public payment flow looks students up by index number (see Phase 0). The `STUDENT` role enum value is reserved for a possible future student portal; nothing in Phase 1 creates a `User`/`UserRole` for a student.

**Historical integrity is structural, not just referential.** `Payment.studentSnapshot` freezes the student's faculty/department/level/category *as they were at payment time*; `RevenueAllocation` freezes the rule name and percentage used. A later reorganization (renaming a faculty, changing a student's department) can never retroactively alter what a historical transaction "was for."

**Financial collections are append-only**: `Payment`, `PaymentStatusHistory`, `RevenueAllocation`, `WalletTransaction`, `WithdrawalRequest`/`WithdrawalApproval`/`WithdrawalSettlement`, `Refund`, `AuditLog` have no soft-delete field and no code path ever deletes or overwrites a historical row — state only moves forward (new rows, or a `status` transition). Structural/config collections get the shared soft-deactivation fields instead.

**Wallet balances are ledger-derived.** `FacultyWallet`/`DepartmentWallet.balancePesewas` is only ever changed in the same multi-document transaction that inserts the corresponding `WalletTransaction` row; that row's unique `{walletType, walletId, sourceType, sourceId}` index makes reposting the same source event (e.g. a payment's revenue allocation, or a withdrawal settlement) a no-op instead of a double-credit.

**Seeding**: `npm run db:seed` (`scripts/seed.ts` → `src/lib/db/seed.ts`) inserts the 9-row `Role` catalog and, if `SUPER_ADMIN_EMAIL`/`SUPER_ADMIN_PASSWORD` are set and no Super Admin exists yet, bootstraps one. Idempotent — safe to re-run.

**Note on `server-only`**: Phase 0 used the `server-only` npm package in `lib/auth/`, `lib/db/`, `lib/validation/`. That package throws unconditionally outside Next.js's own webpack build (it has no way to detect a plain Node process), which broke the seed script run via `tsx`. It's replaced by `src/lib/serverOnly.ts`, a one-line `typeof window !== "undefined"` guard — the same runtime protection (a Client Component bundle can never evaluate this code), but it also works correctly under Node scripts and future test runners.

## Phase 2: Authentication & RBAC

**Session truth moved from the JWT to the database.** The session cookie (`src/lib/auth/session.ts`) now carries only `{ userId, expiresAt }` — role and org/faculty/department scope are no longer embedded in the token. `src/lib/auth/dal.ts`'s `getSession()` (still `cache()`-wrapped, one DB round trip per request) loads the `User` (must be `isActive`) and their active `UserRole` fresh on every call and builds `SessionUser` from that live data. This is why deactivating a user or changing their role takes effect on their very next request instead of waiting out a 7-day token — verified live: deactivating a signed-in user immediately turned their existing session cookie into a 401/redirect, with no token refresh or logout involved.

**Password reset invalidates every existing session immediately.** `User.passwordChangedAt` is set on reset; `getSession()` rejects any token whose `iat` (issued-at) predates it. Verified live: a session created before a password reset stopped working the instant the reset completed, and the pre-reset password was rejected on a fresh login attempt while the new one succeeded.

**`PasswordResetToken`** (`src/models/PasswordResetToken.ts`) — a small addition to the Phase 1 schema list. Single-use: `tokenHash` (SHA-256 of a random 32-byte token; the raw token is never persisted, only emailed), `expiresAt` (1 hour, backed by a Mongo TTL index), `usedAt`. Requesting a reset behaves identically whether or not the email exists, to prevent account enumeration.

**Notifications** (`src/lib/notifications/`): a `NotificationProvider` interface mirroring `lib/payments/provider.ts`, with a `console` implementation that logs to the server console instead of sending real email — a deliberate, scoped-down choice for this phase. Swapping in a real provider (Resend, SendGrid, SES, ...) later is a one-file change; no call site depends on the console implementation directly.

**Authorization**: `src/lib/permissions/can.ts` gained `assertCan()`/`ForbiddenError` — every service function in `src/services/` calls it before touching data, so authorization is enforced at the data-access boundary regardless of which page or action called in. `can.ts` also gained the `user:manage` capability (org-scoped, plus Super Admin) backing account activation/deactivation.

**Audit logging** (`src/lib/audit/recordAudit.ts`): writes one `AuditLog` row per sensitive action (`auth.login`, `auth.login_failed`, `auth.logout`, `auth.password_reset_requested`, `auth.password_reset_completed`, `user.deactivated`, `user.reactivated`). Never throws — a failed audit write is logged to the console rather than blocking the underlying operation, since audit logging must not become a new way to break login.

**Privileged-action confirmation**: `src/components/ui/confirm-dialog.tsx`, a reusable Radix-`Dialog`-based gate — the underlying action only runs after an explicit confirm, and an error from it is shown inline rather than silently closing the dialog. First used for account deactivation/reactivation in `/admin/users`.

**MFA**: schema reservation only, per the spec's "optional... architecture" wording. `User` has nullable `mfaEnabled`/`totpSecretEncrypted` fields; no TOTP flow is implemented. A future phase would add a challenge step between password verification and `createSession()` in `authenticateUser()`.

**UI is intentionally minimal in this phase** — `Button`/`Input`/`Label` primitives and bare Tailwind utility classes, no design-system polish. Per `AGENTS.md`'s own ordering, Phase 3 builds the real design system and rebuilds these shells/dashboards on top of the now-working auth underneath. The role-landing pages (`/super-admin`, `/admin`, `/faculty/[facultyId]`, `/department/[departmentId]`) exist to prove org/faculty/department isolation end-to-end, not as final dashboards — this was verified live for every role tier, including that a Faculty Dean is denied a different faculty's page, a department page, and the org-admin page.

**Known limitation, accepted for this phase**: a password reset invalidates sessions (via `passwordChangedAt`), but there is no "log out all other devices" affordance and no session listing — deactivation and password-reset cover the security-critical revocation cases without building session-management UI.

## Phase 3: Design System & Navigation

Fintech-toned tokens from Phase 0 (`src/app/globals.css`) are now backed by a real component set and a permission-aware navigation shell, replacing the one-line header from Phase 2.

**The nav is data-driven and honest about what exists.** `src/lib/navigation/nav-config.ts#getNavSections(user)` returns Main/Financial/Reports/Administration/Settings sections, but **a section only renders once it has an item for that role** — Financial and Reports are defined as section types with no items yet (no payments/wallets/reports exist), rather than padded with "coming soon" links. `ORG_ADMIN` currently sees Administration → Users; every role sees Settings → Account settings. Phase 4 adds Super Admin's Administration items (Organizations, Platform Users, Audit Logs) directly into this same config — the system doesn't need to change shape, only grow.

**Icons are passed as string keys (`NavIconKey`), never component references**, because `nav-config.ts` is imported from both Server Components (`Sidebar`) and Client Components (`NavSearch`) — a raw component/function reference does not survive serialization across that boundary, but a string does. The actual Lucide icon components are looked up from the key in the one client file that needs them, `nav-content.tsx`.

**Org switcher, search, and notifications are real, not decorative.** `OrgIdentity` shows the organization's actual name (no dropdown, since no user belongs to more than one organization in this schema); `NavSearch` filters and navigates the user's actual nav items client-side; `NotificationsMenu` queries the real (currently empty) `Notification` collection. None of these fabricate data — see the Phase 3 plan's "nav is real" and "notifications are real-but-currently-empty" decisions. Each has a documented extension point for when Phase 4+ gives it more to work with (org management → a real switcher; students/payments → real search; payment/withdrawal events → populated notifications).

**One new real feature**: authenticated change-password (`services/auth.service.ts#changePassword`, `/settings`) — reuses the `passwordChangedAt` session-invalidation mechanism from Phase 2, so changing your password signs you out immediately and redirects to `/login`.

**Responsive shell**: persistent sidebar at `lg:` (1024px+, covers both 1280 and 1440 targets, content capped at `max-w-[1600px]`); a Radix-`Dialog`-based drawer below that, sharing the same `NavContent` list component as the desktop sidebar so the navigation logic exists once. Verified visually (Playwright + real screenshots, not just a passing build) at 1440, 1280, 820 (tablet), and 390 (mobile) widths, logged in as a real seeded Org Admin.

**Bug caught and fixed during visual verification**: the active-nav-item check originally used `pathname.startsWith(item.href + '/')`, which made `/admin/users` match both "Dashboard" (`/admin`) and "Users" (`/admin/users`) as prefixes, highlighting both simultaneously. Fixed in `nav-content.tsx#getActiveHref` to pick the *longest* matching href among a user's nav items, so only the most specific match highlights.

## Phase 4: Super Admin Platform

Super Admin can now actually run the platform end to end — every `Organization`/`Faculty`/`Department`/user before this phase existed only because a throwaway seed script put it there.

**New singleton `PlatformSettings`** (`src/models/PlatformSettings.ts`, fixed `_id: "platform"`, upserted on first read) backs three screens — Platform Settings (name/support email), Global Payment Configuration (environment, currency, card/mobile-money toggles), and Global Revenue Rules (basis-point splits, same sum-to-10000 validation as `RevenueAllocationRule`). It isn't decorative: `organization.service.ts#createOrganization` seeds a new org's first `RevenueAllocationRule` from `defaultRevenueSplits`, so editing the global default has a real, visible downstream effect — verified live by creating an org and confirming its rule matched the platform default.

**Organization admin provisioning reuses Phase 2's password-reset flow instead of a new invite system.** `assignOrgAdmin` creates a `User` with an unusable random password hash and `mustResetPassword: true`, creates the `ORG_ADMIN` `UserRole`, then calls the existing `requestPasswordReset`. Verified live end to end: created an org, added an admin, pulled the console-logged reset link, set a real password through it, and logged in as that admin landing on `/admin`.

**Deactivating an organization now actually cuts off its admins**, not just the UI badge. `src/lib/auth/dal.ts#getSession()` gained a check: if the session's `UserRole.organizationId` points at an `Organization` that is no longer `isActive`, the session is rejected — the same live-DB-check pattern Phase 2 established for user deactivation, extended to the org level since Phase 4 is what makes organization deactivation a real, reachable action for the first time. Verified live: deactivating an org while its admin was signed in killed that session on the very next request.

**Dashboard metrics are real aggregation queries** (`dashboard.service.ts`) across `Organization`, `Student`, `Payment`, `FacultyWallet`, `DepartmentWallet`, `WithdrawalRequest`, `WithdrawalSettlement` — and mostly return zero today, honestly, since no payment flow exists yet (Hubtel integration is still just the Phase 0 interface). Nothing is fabricated to make the dashboard look busier than the platform actually is.

**Only one chart was built.** Running the `dataviz` skill's palette validator against the existing success/pending/danger status trio as a categorical chart palette failed colorblind-adjacency (`ΔE 5.3` protan, `12.7` normal-vision — both below the required floor) — reworking colors already shipped across every status badge in the app wasn't worth it for a payments-by-status chart when those counts are already required as individually-labeled stat tiles (the allowed pattern: status color **with** a label, never color alone). The one real chart — transaction volume, last 14 days — is a hand-rolled single-hue SVG bar chart (`components/finance/volume-trend-chart.tsx`), so no adjacency problem applies, with a hover tooltip and a visually-hidden data table for accessibility, per the skill's mark spec.

**A real bug was caught by live verification, not by `tsc`/`lint`/`build`.** `platform.service.ts#getPlatformSettings` originally returned `doc.defaultRevenueSplits` — a Mongoose subdocument array — straight through to `PaymentConfigForm`/`RevenueRulesForm` (Client Components). Mongoose subdocuments carry circular internal references (parent pointers, schema refs) that are not plain, RSC-serializable data; passing them across the server/client boundary crashed every settings page with a 500 (`RangeError: Maximum call stack size exceeded`, `Object.hasOwn`) — invisible to the type checker, since Mongoose's types don't distinguish a subdocument from a plain object. Fixed by mapping to plain `{ beneficiaryType, percentageBps }` objects in the DTO. Caught by actually driving the built app with Playwright and reading the dev server's error log, not by trusting a passing build — the same lesson as Phase 3's nav-highlighting bug, now for a server-side crash instead of a visual glitch.

**Known limitation, accepted for this phase**: Audit Logs is a plain latest-200 list, no filtering or pagination yet — real data (Phase 2 wired `recordAudit` into every sensitive action), just not filterable yet. Platform Users has no bulk actions. Revoking an org admin deactivates the `UserRole`, not the `User` — consistent with Phase 1's role-history model, the account can be reassigned a role later without recreating it.

## Phase 5: Organization Admin

Org Admin can now actually stand up their organization — before this phase, every `Faculty`/`Department`/`AcademicLevel`/`StudentCategory`/`PaymentPeriod` in the database existed only because a throwaway seed script put it there, and the only role ever assignable was another Org Admin (Phase 4).

**One shared activation helper replaced three duplicated blocks.** `src/lib/db/scoped-activation.ts#setEntityActive` is now used by `Organization`, `User`, `Faculty`, `Department`, `AcademicLevel`, `StudentCategory`, `PaymentPeriod`, and `DuesConfiguration` — the exact activate/deactivate block that used to be hand-duplicated in `organization.service.ts` and `user.service.ts` is now one function. Re-verified live afterward (org and user deactivate/reactivate still work).

**New capability `organization:administer`, kept separate from `organization:manage`.** Org Admin needed real authority over their own org's structure and profile, but `organization:manage` gates Super-Admin-only actions from Phase 4 (deactivating an organization, assigning/revoking its Org Admin). Broadening that capability instead would have let an Org Admin deactivate their own organization or revoke a peer Org Admin — a privilege-escalation bug, not a convenience. `organization:administer` is scoped identically (`isSuperAdmin(user) || (ORG_ADMIN && inOrganization(...))`) but reserved for the new Phase 5 actions (profile edit, academic level/student category/payment period CRUD, org-scoped audit log, org dashboard). `faculty:manage`, `department:manage`, and `dues:configure` (all from Phase 0) were reused as-is.

**User & Role Management generalizes Phase 4's org-admin-only flow via refactor, not duplication.** `src/services/role-assignment.service.ts#assignRole`/`revokeRoleAssignment` handle any of the 7 org-scoped roles, with role-appropriate scope validation (a faculty role requires a real `Faculty` in this org; a department role requires a real `Department`, and derives its `facultyId` automatically). `organization.service.ts#assignOrgAdmin`/`revokeOrgAdmin`/`listOrgAdmins` (Phase 4) became thin wrappers around these — Phase 4's Super Admin screen needed zero changes and was re-verified live to still work. `/admin/users` now shows role, faculty/department scope, and account status together, with both "revoke role" (removes access, keeps the account for later reassignment) and "deactivate account" (blocks login outright) as distinct actions, since they're genuinely different things.

**Payment period "current" toggle is sequential updates, not a transaction** — deliberately. This is non-financial housekeeping, and the local standalone MongoDB (no replica set) doesn't support multi-document transactions at all; true transactions stay reserved for actual money movement once that's built. A partial failure here just means no period is marked current for a moment, recoverable by re-clicking.

**Dues Configuration's optional scoping selects are independent, not cross-filtered** — no client-side "faculty narrows department options" logic in this pass, kept simple for an MVP config screen.

**Verified live end to end** (Playwright, same approach as Phases 3–4): created a faculty, a department under it, an academic level, a student category, and a payment period (marked current) as a real seeded Org Admin; assigned a Faculty Dean and a Department HOD through the new role-assignment flow (not a seed script) and confirmed both could set their password via the real console-logged reset link and land on their existing Phase 2 `/faculty/[id]`/`/department/[id]` pages; created a dues configuration referencing the new period and faculty; confirmed the dashboard's stat tiles and recent-activity feed reflected all of it. Zero console errors throughout.

## Phase 6: Academic Structure depth

Faculty and Department management from Phase 5 gained edit, a detail/statistics view, executive visibility, and two validation rules the spec called out that Phase 5 didn't enforce.

**Duplicate-name checks are case-insensitive and safely escaped.** `src/lib/db/escape-regex.ts#escapeRegExp` sanitizes user input before it's used to build a MongoDB case-insensitive regex match — without it, a name containing regex metacharacters (`(`, `.`, `*`, ...) could throw, match too broadly, or become a ReDoS vector. Used by both `faculty.service.ts#assertUniqueFacultyName` and `department.service.ts#assertUniqueDepartmentName` (the latter scoped to `{organizationId, facultyId}`, matching the existing code-uniqueness scope). Verified live: creating "faculty of science" when "Faculty of Science" already existed was correctly rejected.

**"A department may belong to only one active faculty at a time" is now an enforced rule, not just the data model's shape.** `department.service.ts#assertActiveFacultyInOrganization` rejects `createDepartment`/`updateDepartment` when the target faculty is deactivated. Verified live: after deactivating a test faculty, it correctly disappeared from the department-creation faculty `<select>`.

**Edit is a view+edit combined detail page**, matching the `/admin/profile` pattern from Phase 5 — `/admin/faculties/[facultyId]` and `/admin/departments/[departmentId]` show statistics, the executives/HOD list, and an inline pre-filled edit form together, rather than a separate `/edit` route. Both list pages (`FacultiesTable`/`DepartmentsTable`) gained a "View" link per row.

**"Statistics" and "executives" are direct queries added to the existing services**, the same shape Phase 4/5's dashboard metrics already use — `getFacultyDetails` adds a department count, a student count, and a `UserRole` query filtered to the three faculty-level roles; `getDepartmentDetails` mirrors it for the three department-level roles and additionally calls out the `DEPT_HOD` row specifically. No new shared abstraction needed.

**Verified live end to end**: duplicate-name rejection (case-insensitive), faculty edit (name/code) persisting correctly, an existing faculty's detail page showing its real Dean and department count, a deactivated faculty correctly excluded from department assignment, and an existing department's detail page showing its real HOD by name and email. Zero console errors throughout.

## Phase 7: Student Categories & Academic Levels depth

Both entities were already configurable DB rows, not hard-coded (Phase 5). This phase closed the remaining gaps the spec called out by name: Edit, Reorder, and "preserve historical references" — the last of which turned out to be a real, previously-unnoticed bug rather than something already satisfied.

**`Payment.studentSnapshot` now freezes names alongside ids** (`facultyName`, `departmentName`, `academicLevelName`, `studentCategoryName`, all optional, added to the schema and to `shared/types.ts#StudentSnapshot`). Before this phase the snapshot stored only ids — harmless while Faculty/Department/AcademicLevel/StudentCategory were immutable, but Phase 6 made Faculty/Department renameable and this phase makes AcademicLevel/StudentCategory renameable too, which would have let a rename silently rewrite what a historical payment record displays. No `Payment` rows exist yet (the payment flow isn't built), so this was a free schema change now rather than a migration later — but it had to happen in this phase, since it's the actual mechanism behind "preserve historical references," not a follow-up.

**`StudentCategory` gained `sortOrder`**, mirroring the field `AcademicLevel` already had since Phase 5 — required for "Reorder" to mean anything for categories.

**Duplicate-name checks extend Phase 6's exact pattern to these two entities.** `academic-level.service.ts#assertUniqueAcademicLevelName` and `student-category.service.ts#assertUniqueStudentCategoryName` are the same case-insensitive, `escapeRegExp`-sanitized shape as Phase 6's `assertUniqueFacultyName`/`assertUniqueDepartmentName` — each service keeps its own local copy rather than sharing one generic function, consistent with how Faculty and Department already do it independently.

**Reorder swaps the moved row with its neighbor, then renumbers the whole list sequentially (0..n-1) rather than swapping raw `sortOrder` values.** A plain value-swap would be a silent no-op whenever two rows already shared a `sortOrder` — which was already the case for every row created through the Phase 5 inline form, since its "Sort order" input defaults to `0` and most users never change it. `moveAcademicLevel`/`moveStudentCategory` (`src/services/{academic-level,student-category}.service.ts`) re-sort the full list by current `sortOrder`, swap the moved row with its up/down neighbor by array position, then write back sequential integers — sequential updates, no transaction, same non-financial-housekeeping reasoning as Phase 5's payment-period "set current" toggle.

**Edit and reorder live on the existing list page, not a new detail page.** Unlike Faculty/Department (Phase 6), which have real related data worth a dedicated view, these are flat name/code/order rows — proportionate treatment is a small edit dialog, not a whole route. `src/components/ui/edit-dialog.tsx` is the new, generic edit-form shell (the edit counterpart to `ConfirmDialog`): fields are passed as children, the whole form is collected as `FormData` on submit, and a thrown error surfaces inline instead of closing the dialog. Both `academic-levels-table.tsx` and `student-categories-table.tsx` gained an Edit button (opening `EditAcademicLevelForm`/`EditStudentCategoryForm`, each a thin wrapper around `EditDialog`) and plain Up/Down reorder buttons per row (no confirmation dialog — reordering isn't destructive, the same treatment as Phase 5's "Set as current" button).

**New organizations are seeded with the spec's own example rows.** `organization.service.ts#createOrganization` now also inserts four `AcademicLevel` rows (100/200/300/400, sequential `sortOrder`) and three `StudentCategory` rows (Fresher/Continuing/Top-up, sequential `sortOrder`) alongside the default revenue-split rule it already seeded in Phase 4. These are ordinary rows from the moment they exist — editable, deactivatable, reorderable — not hard-coded logic; verified directly against MongoDB after creating a new organization live (four `AcademicLevel` and three `StudentCategory` documents, correct names/codes/`sortOrder`, all `isActive: true`).

**Verified live end to end**: duplicate-name rejection (case-insensitive) for both academic levels and student categories, confirming no row is actually created on rejection; edit persisting a renamed level/category; reorder (Up button) persisting after a full page reload; a brand-new organization, created live as Super Admin, confirmed pre-seeded with exactly the four academic levels and three student categories by querying the database directly. Zero console/page errors throughout.

## Phase 8: Payment Period Management

`PaymentPeriod` existed since Phase 5, but only as `name`/`code`/`startDate`/`endDate` plus the generic `isActive`/`isCurrent` boolean pair every Phase 5 entity got. This phase's spec calls for a real 5-state lifecycle (Draft → Scheduled → Active → Closed → Archived), two more date fields, an academic-year grouping field, and a description — a boolean pair can't express that, so the model, service, and UI were rewritten around a proper `status` enum rather than adding `status` alongside the old flags.

**`isActive`/`isCurrent` are gone, not deprecated.** Carrying both the old boolean pair and the new `status` field would let a period be simultaneously `ARCHIVED` and `isActive: true` — exactly the kind of invalid configuration this phase exists to prevent. `status` now carries both former meanings: `ARCHIVED` is what `isActive: false` used to mean (retired, historical), `ACTIVE` is what `isCurrent: true` used to mean (the operative period). The old partial-unique index on `{organizationId}` filtered to `isCurrent: true` became the same index filtered to `status: "ACTIVE"` — at most one Active period per organization at a time, the same invariant, expressed through the new field. `src/lib/db/scoped-activation.ts#setEntityActive` is no longer used by this entity (every other Phase 5 entity keeps using it as before).

**Status transitions are a fixed adjacency map, not a free-for-all.** `payment-period.service.ts#PAYMENT_PERIOD_TRANSITIONS`: `DRAFT → SCHEDULED | ARCHIVED`; `SCHEDULED → DRAFT | ACTIVE | ARCHIVED`; `ACTIVE → CLOSED`; `CLOSED → ARCHIVED`; `ARCHIVED` is terminal. `transitionPaymentPeriodStatus` rejects anything outside this map with a message naming the current status, and separately re-checks the one-Active-at-a-time constraint before allowing a move to `ACTIVE`, throwing a friendly error naming the currently-active period rather than surfacing a raw Mongo duplicate-key error. New periods always start at `DRAFT` — status is never settable at creation, only reached by walking the map. `ARCHIVED` periods reject edits outright (`updatePaymentPeriod` checks status first) since they're meant to be historical record.

**The two date pairs are validated independently, not against each other.** `endDate` must be after `startDate`, and `paymentCloseDate` must be after `paymentOpenDate` — but the payment window is deliberately *not* constrained to fall inside the academic start/end dates, since real payment windows legitimately open before a term starts (early-bird) or extend past its end (late-payment grace period). Duplicate-name checking reuses Phase 6/7's exact pattern (case-insensitive, `escapeRegExp`-sanitized, each service keeping its own local copy rather than sharing one generic function).

**The detail page pattern (Phase 6), not the edit-dialog pattern (Phase 7), because of field count.** Eight fields including two date-range pairs and a status enum is too much for Phase 7's compact modal — `/admin/payment-periods/[paymentPeriodId]` shows the full period, an edit form (hidden once Archived), and a `PaymentPeriodStatusActions` component that renders only the transitions actually valid from the current status (computed server-side from `PAYMENT_PERIOD_TRANSITIONS` and passed down as plain data), each behind the existing `ConfirmDialog` since a status change is a real, consequential action.

**A real cross-boundary gotcha, caught before it shipped, not after**: the new `status-badge.tsx` and `payment-period-status-actions.tsx` are Client Components, and importing `PaymentPeriodStatus` or the label/transition maps as runtime values from `payment-period.service.ts` would pull `@/lib/serverOnly`'s guard into the client bundle — the same class of problem Phase 1 solved for `tsx` scripts, here hitting the browser bundle instead. Both files use `import type` only for anything sourced from the service, with their own small local copies of the status→label/variant maps, matching the `import type`-only pattern every other Client Component in the app already uses for its service's summary types.

**Downstream call sites updated, not left stale**: `dashboard.service.ts`'s "current period" lookup moved from `{ isCurrent: true }` to `{ status: "ACTIVE" }`; `dues-configurations/page.tsx`'s payment-period picker moved from filtering `isActive` to excluding `ARCHIVED` only — a dues configuration can validly reference a Draft, Scheduled, Active, or Closed period, just not a retired one.

**Verified live end to end**: invalid-date rejection for both date pairs (end-before-start, close-before-open); duplicate-name rejection (case-insensitive) with no row created; a new period landing in Draft; edit persisting after reload; the full Draft → Scheduled → Active → Closed → Archived walk, with only the valid next steps ever offered at each stage (confirmed Draft never offers "Activate" directly, Active only offers "Close", Closed only offers "Archive"); a second period correctly blocked from activating while another was already Active, and successfully activating once the first was closed; the dues-configuration period picker including the Active period and excluding the Archived one; the dashboard's "current period" tile reflecting the Active period. Zero unexpected console/page errors — the one 500 logged was the deliberate, expected rejection of the blocked second activation, the same server-side error shape every other `ConfirmDialog`-driven action in the app already produces.

## Phase 9: Dues Configuration Engine

`DuesConfiguration` existed since Phase 5 as a flat entity — name/code/amount/optional scope/period/`isMandatory`, with the generic Phase 5 `isActive` boolean. This phase makes it the entity the rest of the payment system will depend on most: a real `status` lifecycle, an `effectiveDate`, automatic amount resolution for a paying student, a structural guarantee that students can never supply their own amount, protection against silently-colliding active configurations, and a genuinely capable admin UI (search/filter table + multi-step wizard) replacing the old one-row inline form. No public payment-initiation flow exists yet (Hubtel integration is still just an interface) — "automatically determine the amount" and "students must never modify it" are fulfilled *now* by building the resolver as a real, tested service function with **no amount parameter anywhere in its signature**, ready for that future flow to call.

**`status: "DRAFT" | "ACTIVE" | "ARCHIVED"` replaces `isActive`**, the same reasoning as Phase 8's `PaymentPeriod`: carrying both would allow contradictory state. Unlike a payment period, a dues configuration has no `SCHEDULED`/`CLOSED` middle states — it doesn't "close" on its own, it's just retired (`ARCHIVED`, terminal) when superseded. `Draft → Active | Archived`, `Active → Archived` — `transitionDuesConfigurationStatus` (`src/services/dues-configuration.service.ts`) rejects anything else.

**A department always implies its faculty, enforced server-side, never trusted from the form.** `resolveFacultyId()` derives `facultyId` from the selected department's own `facultyId` record whenever a department is chosen; a separately-submitted `facultyId` that disagrees is rejected outright rather than silently overridden — the same "derive scope from the child" rule Phase 5 established for department-level role assignment. This is what makes specificity-based resolution (below) sound: a department-scoped configuration is always also faculty-scoped, so it always outranks a faculty-only one.

**"Prevent overlapping active configurations" means scope collision, not date-range math.** The spec's field list gives a single `effectiveDate`, not a range, so "overlap" is two **Active** configurations sharing the exact same scope key (`paymentPeriodId` + the four optional scope fields, nulls included). `assertNoActiveOverlap()` rejects publishing (create-as-Active, or a Draft→Active transition) whenever another Active configuration already shares that key — same "close X before activating another" friendly-error shape as Phase 8. **Drafts never participate in the check**, so an admin can stage a same-scoped replacement while the old one is still live, then archive the old one and publish the new one. A narrower scope is never rejected against a broader one — that's not a collision, it's exactly the fallback-plus-override shape the resolver is built to handle.

**`resolveApplicableDuesConfiguration()` is the literal, structural answer to "students must never modify the amount"** — there is no amount parameter to modify; the amount is looked up from Active, currently-effective (`effectiveDate <= now`) configurations matching the student's scope, ranked by **specificity** (how many of the four optional scope fields are pinned, 0–4), ties broken by latest `effectiveDate` then latest `createdAt`. It takes no `SessionUser`/`assertCan` — deliberately, since its real caller will eventually be an unauthenticated student-facing payment flow, not an org-admin action (mirroring `can.ts`'s existing note on `payment:record`: "student-initiated; verified server-side ... not by role"). No route calls it yet, so it was verified with a standalone script seeding an org-wide Active configuration and a more specific Faculty-scoped one, confirming the specific one wins for a matching student, the general one wins for everyone else, and the overlap check rejects a second Active configuration in the same scope — all four checks passed, then the script cleaned up after itself.

**Historical payments will preserve what they actually charged.** `Payment.duesConfigurationSnapshot` (`{ name, code, amountPesewas, effectiveDate }`, required) mirrors the `studentSnapshot` pattern from Phase 1/7 — once a payment exists, later edits or even archival of the live `DuesConfiguration` row can never change what that payment shows it charged. Free schema change now, since no `Payment` rows exist yet.

**The multi-step wizard is a bespoke component, not a reuse of `EditDialog`.** `EditDialog` (Phase 7) assumes one `<form>` submitted whole; a wizard needs controlled state carried across steps, so `dues-configuration-modal.tsx` is its own Radix-`Dialog`-based component (same overlay/content chrome) serving both create (Scope → Details → Review, with "Save as draft" / "Publish now") and edit (same steps, "Save changes" only, hidden once `ARCHIVED`) — one implementation, not two. A real, if minor, UX bug was caught and fixed during live verification: both submit buttons shared one `pending` boolean, so activating either showed *both* "Saving…" and "Publishing…" busy-labels at once; fixed by tracking which specific action is in flight (`pendingAction: "draft" | "publish" | "save" | null`) instead of a plain boolean.

**The table's search/filters are client-side over the already-fetched list**, the same "fetch once, filter in the browser" approach as Phase 3's `NavSearch` — no new pagination or server-search infrastructure, matching how much data one organization realistically has. `dues-configurations-toolbar.tsx` holds all the filter state (search text + six dropdowns: status, category, level, period, faculty, department) and composes `dues-configurations-table.tsx` underneath it.

**Another Mongoose/TypeScript populate gotcha, distinct from the Phase 5 one.** Even a single `.populate<T>([...])` call across six paths produces a document type (`MergeType<any, T>`) that doesn't structurally match a hand-written parameter type for a separately-named mapper function — TypeScript reports the merged type as "missing" the base document's own fields, though every field is genuinely present at runtime. Rather than inlining the ~15-field mapping twice (the fix Phase 5's original chained-`.populate()` gotcha required), this one is worked around the same way `scoped-activation.ts` already handles a different Mongoose typing gap: the mapper's parameter is typed `any` with a comment explaining why, keeping its *return* type strictly `DuesConfigurationSummary` so every caller still gets full type safety.

**Verified live end to end**: the full wizard flow (Scope → Details → Review) creating a Draft; activating it; publishing a second, identically-scoped configuration directly rejected with the overlap error while saving the same scope as a Draft still succeeds; editing an Active configuration's amount and confirming it persists; archiving it (Edit button disappears, immutable); the previously-blocked duplicate Draft successfully activating once the original was archived; the search box and the status filter both correctly narrowing the table; "Created by" showing the real admin's name. Zero unexpected console/page errors — the 500s logged were the deliberate, expected overlap rejections, the same server-side error shape every other action-driven mutation in the app already produces.

## Phase 10: Student Payment System

The first real, public, unauthenticated payment flow — everything prior built the administrative side; this is what a student actually uses. Several pieces already anticipated this phase: `proxy.ts` already whitelisted `/pay` as public and `/api/*` already bypassed the proxy entirely (Phase 0), `Organization.slug`'s own doc-comment says it "stays immutable to avoid breaking the public payment URL," and `PlatformSettings.paymentEnvironment: "SANDBOX" | "LIVE"` (Phase 4) already existed, defaulting to `SANDBOX`, unconsumed until now.

**No pre-existing `Student` roster row is required to pay.** `Payment.studentSnapshot`'s scope fields have been optional since Phase 1, and `Payment.studentIndexNumber` is a plain string, not a hard foreign key — the schema was never built to require a roster match at payment time (`StudentPaymentMatch`, Phase 1, is explicitly a *later*, separate reconciliation concern). The student self-declares index number, full name, academic level, and student category (the four items the spec named) plus optional faculty/department and contact info; the amount is never a form field anywhere — it's resolved server-side by Phase 9's `resolveApplicableDuesConfiguration` and re-resolved (never trusted from the client) at the moment the `Payment` row is created.

**No real Hubtel sandbox account exists, so `paymentEnvironment` selects between two `PaymentProvider` implementations.** `HubtelProvider` is implemented for real, per Hubtel's public Checkout API shape, but untested against a live account — the same disclosed boundary every phase has kept. `SandboxPaymentProvider` is an in-app checkout simulator ("Simulate Successful/Failed/Cancelled") used while `paymentEnvironment` stays at its default — not fake application data, but the same test-mode concept every real gateway ships, built in-house because this environment has no access to Hubtel's. This is what makes every payment status and the receipt path provably testable here.

**The public flow**: `/pay/[orgSlug]` (entry form) → provider checkout (`/pay/[orgSlug]/sandbox-checkout/[clientReference]` in sandbox mode) → `/pay/[orgSlug]/status/[clientReference]` (client-side poller, redirects to the receipt once `SUCCESSFUL`) → `/pay/[orgSlug]/receipt/[clientReference]` (only renders once `SUCCESSFUL`; shows the preserved gateway transaction reference and a generated receipt number). New public-safe list functions (`listPublicFaculties`, `listPublicAcademicLevels`, etc.) were added alongside the existing admin-scoped `assertCan`-gated ones, since the student-facing form has no `SessionUser` at all.

**QR code**: the `qrcode` package (a real dependency addition — hand-rolling a QR/Reed-Solomon encoder isn't reasonable scope, unlike the UI primitives this project otherwise builds in-house) renders a server-side data URI on `/admin/profile`, encoding the org's own `/pay/[slug]` URL.

**USSD**: `/api/ussd` implements the standard aggregator session contract (`{sessionId, phoneNumber, text}` in, `CON`/`END` text out), with session state persisted in a new `UssdSession` collection (TTL-expired) since USSD is stateless per request. No live telecom short code is reachable from this environment — verified via direct simulated HTTP requests, the same way the webhook routes are.

**Verified live**: the full successful-payment path end to end (correct amount, dues configuration name, receipt number, preserved `SBX-` provider reference, student name and index number all appearing correctly on the receipt); the failed and cancelled terminal states rendering distinctly on the status page; a full USSD session (welcome → index number → name → dynamically-generated level/category menus from real DB data → confirm → cancel); the QR code decoding to the correct URL. Zero console/page errors.

## Phase 11: Payment Gateway Architecture

Phase 10 built the `PaymentProvider` interface and a first webhook handler; Phase 11 hardens it into what the spec asks for by name — `initializePayment`/`verifyPayment`/`processWebhook`/`refundPayment`/`getTransaction` — and closes a real gap the rename surfaced: the original webhook handler's idempotency was **check-then-act** (`findOne` → compare status → `.save()`), which has a genuine race between two near-simultaneous webhook deliveries. It also never allocated revenue or credited a wallet, because nothing had, since Phase 1 — `RevenueAllocationRule`/`RevenueAllocation`/`FacultyWallet`/`DepartmentWallet`/`WalletTransaction` had existed as unused schema since the very beginning.

**The idempotency mechanism this phase needed was already designed into that schema.** `RevenueAllocation` has carried a unique index on `{paymentId, beneficiaryType, beneficiaryId}` since Phase 1; `WalletTransaction` has carried one on `{walletType, walletId, sourceType, sourceId}` since Phase 1. Neither had ever been wired to real logic before now.

**Webhook idempotency is one atomic, conditional update, not a read-then-write.** `recordPaymentOutcome` (`src/services/payment.service.ts`) now does `Payment.findOneAndUpdate({ providerReference, status: "PENDING" }, { $set: {...} }, { new: true })`. MongoDB serializes writes to the same document, so of two concurrent or redelivered webhooks for the same transaction, only the one that still finds `status: "PENDING"` at the moment it runs actually applies the update — the other gets `null` back, a safe, silent no-op (distinguished from "payment doesn't exist" via one follow-up `findOne`, only for the error message). This applies uniformly to every outcome, not just successful ones. Revenue allocation is called only from inside the branch that just proved, via the update actually returning a document, that *this* request performed the transition — structurally, nothing can double-allocate for one payment. **Verified directly**: firing the identical sandbox webhook payload at `recordPaymentOutcome` twice with `Promise.all` (a genuine concurrent race, not just a sequential duplicate) produced exactly one `PaymentStatusHistory` row, exactly one `RevenueAllocation` per attributable split, and exactly one wallet credit — a third, sequential duplicate afterward was confirmed to still be a no-op.

**Revenue allocation (`src/services/revenue-allocation.service.ts`) reuses Phase 9's specificity-resolution shape exactly.** `RevenueAllocationRule` has carried optional `appliesToFacultyId`/`appliesToDepartmentId` scoping fields since Phase 1, unused until now — `resolveApplicableRevenueRule` ranks matching active rules by how many of those two fields are pinned, tie-broken by `priority` then recency, the same reasoning `resolveApplicableDuesConfiguration` already uses. A split whose beneficiary can't be resolved (the payment carries no faculty/department) is skipped, not thrown; `ORGANIZATION`-type splits get a `RevenueAllocation` audit row but no wallet credit, since no wallet model exists for the organization's own cut, by the original Phase 1 design.

**Wallet crediting is ledger-first, not balance-first — the only available atomicity primitive without a replica set.** `creditWallet` inserts the `WalletTransaction` row *before* incrementing `balancePesewas`; a duplicate insert throws E11000, is caught, and the balance is never touched twice. This ordering is deliberate: this MongoDB instance has no replica set and therefore no multi-document transactions — the exact tension Phase 1's own notes flagged as deferred "until actual money movement is built." The accepted, disclosed trade-off: `WalletTransaction.balanceAfterPesewas` (a per-row historical annotation) can be marginally stale under a genuine concurrent-but-*unrelated* credit race to the same wallet; `balancePesewas` itself is never wrong, since every increment is atomic and gated by that same insert. **Verified directly**: concurrent refund-reversal calls (`Promise.all`) against the same payment debited the wallet back to its exact original balance, not below it.

**Refunds (`src/services/refund.service.ts`) make `refundPayment()` a real, load-bearing capability, not an interface method nothing calls.** New `payment:refund` capability (`can.ts`), scoped to `ORG_ADMIN`. `processRefund` supports full refunds only for this pass — a partial refund would need a `PaymentStatus` this codebase doesn't have yet (`PARTIALLY_REFUNDED`), stated as out of scope rather than half-built. Requires the payment to be `SUCCESSFUL`; on a successful gateway refund, reverses every `RevenueAllocation` tied to that payment via `debitWallet` (same ledger-first idempotency), and flips `Payment.status` to `REFUNDED` through the same atomic-guard pattern (`status: "SUCCESSFUL"` in the filter) so calling it twice is rejected, not double-processed. No admin UI was built for triggering a refund in this pass — the same "service is real, UI wasn't asked for" boundary Phase 9 drew around its resolver.

**`getTransaction()` is a deliberately richer read than `verifyPayment()`** — channel, raw gateway payload, intended for reconciliation/display rather than driving status transitions. Sandbox's `verifyPayment`/`getTransaction` continue to throw "not supported" (Phase 10's original design) — sandbox has no independent gateway-side record; outcomes only ever arrive via the simulated webhook.

**Verified**: the full idempotency and revenue-allocation suite above, via a standalone script mirroring Phase 9's resolver-verification approach (seed real data, exercise the service functions directly — including genuine concurrent races via `Promise.all` — assert outcomes, clean up). `tsc`/`lint` clean.

## Phase 12: Payment Administration

Phases 9–11 built the whole payment pipeline but gave Org Admins no way to see any of it. Phase 12 is that missing admin surface — Payment Records, Payment Details, Duplicate Payment Review, Payment Monitoring, and Collection Reports — built entirely on data Phase 11's idempotency work already made trustworthy. One constraint runs through every screen: **administrators can never manually mark an unconfirmed payment as successful.** Every page here is read-only with respect to `Payment.status`, with exactly one exception — refunding an already-`SUCCESSFUL` payment (the reverse direction, going through the real gateway), which is also where `processRefund` (Phase 11, built with no UI trigger at the time) finally gets one.

**Payment Records is server-driven, a deliberate departure from every prior admin table.** Faculty, Dues Configuration, and every other Phase 5–9 table fetch their whole (small, bounded) collection once and filter client-side. `Payment` grows without bound as students pay every period, so `listPayments` applies every filter (search, status, faculty, department, category, level, period, date range) and pagination at the MongoDB level, and the filter form is a plain `<form method="get">` — no client JS at all, filter state lives entirely in the URL's search params, and the whole page (form, table, pager) is a Server Component. This also means the table only needs one extra query per page load, not one per row: after fetching a page of payments, one `RevenueAllocation.find({paymentId: {$in: [...]}})` call fetches every allocation for that page at once, merged in-memory into `facultyAllocationPesewas`/`departmentAllocationPesewas` — real per-payment allocation amounts, not the student's faculty/department name repeated under a different column header.

**"Duplicate" has a concrete, checkable definition, not a fuzzy heuristic.** Students pay by index number with no account, so nothing stops the same person paying the same dues configuration twice, and the system can't prevent it at creation time — a student unsure their first attempt went through has no account to check. `getDuplicatePaymentGroups` is a `$group` aggregation on `{studentIndexNumber, duesConfigurationId}` filtered to `status: "SUCCESSFUL"`, matched to groups with `count > 1`. Duplicate Payment Review is the first real place `processRefund` gets a UI trigger — a `RefundAction` component (new, shared with the Payment Details page) built on `EditDialog` rather than `ConfirmDialog`, since a refund needs a reason field, not just a yes/no. `EditDialog` gained a `submitVariant` prop for this (mirroring `ConfirmDialog`'s existing `confirmVariant`) so the in-dialog submit button reads as destructive too, not just its trigger.

**Payment Monitoring's "stale pending" list is a real operational signal, not decoration** — `PENDING` for over 30 minutes means either an abandoned checkout or a webhook that never arrived, either way something worth an admin's attention. Verifying this against seeded data surfaced a real Mongoose behavior worth knowing: `Payment.updateOne(..., {$set: {createdAt: staleDate}})` silently did nothing — Mongoose's `timestamps` plugin protects `createdAt` from query-based updates by default — so backdating test data for verification had to go through the raw driver (`Payment.collection.updateOne(...)`), bypassing Mongoose entirely. Not an application bug (three genuinely old leftover payments from earlier-phase testing correctly appeared in the stale list throughout), purely a test-script lesson.

**Collection Reports reuses `VolumeTrendChart` (Phase 4) directly, unmodified** — it was already fully props-driven with no Super-Admin-specific logic, so `getOrgTransactionVolumeTrend` (an org-scoped sibling of `dashboard.service.ts#getTransactionVolumeTrend`, same aggregation shape) is a real reuse, not a rebuild. Per the `dataviz` skill's Phase 4 finding that the status-color trio still isn't colorblind-safe as a categorical palette, no new chart was added for status breakdowns — those stay individually-labeled numbers, the same restraint Phase 4 exercised.

**Verified live end to end**: seeded a realistic mix (two `SUCCESSFUL` payments sharing an index number and dues configuration, one `FAILED`, one `CANCELLED`, one genuinely stale `PENDING`, one fresh `PENDING`) via the real `initiatePayment`/`recordPaymentOutcome` pipeline, not hand-written rows. Payment Records' search correctly narrowed by index number and excluded unrelated rows; the status filter correctly isolated `FAILED`; the Faculty/Department allocation columns showed real, correct amounts; the payment detail page showed the right status history and a revenue-allocation breakdown that summed exactly to the payment amount; Duplicate Review surfaced the seeded group, and refunding one member from there correctly dropped the group below the duplicate threshold and correctly excluded that payment from Collection Reports' totals (confirmed against a hand-computed sum of the remaining real `SUCCESSFUL` payments in the database, not an assumption); Monitoring correctly flagged the stale payment and showed accurate status counts; no control anywhere in this phase can set a payment to `SUCCESSFUL` directly. Zero console/page errors. All seeded test data and wallet balances were cleaned up afterward.

## Phase 13: Revenue Distribution Engine

Phase 11 wired real revenue allocation for the first time, but on a percentage-split model (`RevenueAllocationRule.splits`, an array summing to 100% across `ORGANIZATION`/`FACULTY`/`DEPARTMENT`). The spec's actual formula — `departmentShare = totalAmount - facultyShare - approvedDeductions` — is a different model entirely: Faculty's share defaults to a **fixed cash amount**, not a percentage of what was paid. The spec's own worked examples prove it — a GH₵100 payment splits Faculty 20 / Department 80, and a GH₵75 payment *on the same rule* splits Faculty 20 / Department 55. No percentage could ever hold Faculty's absolute amount constant across two different payment amounts; only a fixed value can. This phase's model supersedes Phase 11's wholesale, the same way Phase 8/9 replaced earlier incompatible shapes.

**`RevenueAllocationRule` (`src/models/RevenueAllocationRule.ts`), redesigned**: the `splits` array and the implicit Organization cut are gone, replaced by `facultyShareType: "FIXED" | "PERCENTAGE"` plus the matching `facultyShareAmountPesewas` or `facultyShareBps`, and five optional scope dimensions (`paymentPeriodId`, `facultyId`, `departmentId`, `academicLevelId`, `studentCategoryId` — all null-as-wildcard). Department is never a configured share; it structurally receives whatever the formula leaves over. An organization's own commission, if any, is no longer a hardcoded third split — it's expressed as one configured `RevenueDeduction` like any other, since nothing forced a fixed "house cut" to exist. `createOrganization`'s seeding (`organization.service.ts`) now creates one org-wide `PERCENTAGE`-mode rule from the platform's existing Faculty default split (`PlatformSettings.defaultRevenueSplits`, Phase 4) — that platform-level shape itself is untouched, only how a new org's first rule is derived from it changed.

**`RevenueDeduction` (`src/models/RevenueDeduction.ts`) is genuinely new** — nothing in the schema represented "money taken off the top before Department gets the remainder" until now. Same five-dimension scope shape as the rule, `deductionType: "FIXED" | "PERCENTAGE"`, and a `status: "DRAFT" | "APPROVED" | "ARCHIVED"` lifecycle mirroring Phase 8/9's create-as-Draft-then-explicitly-transition pattern — a deduction affects nothing until explicitly approved. Deductions are **additive, not single-best-match**, unlike the one rule that resolves per payment: every `APPROVED`, scope-matching deduction is summed, since a platform fee and a processing fee can legitimately both apply to the same payment, while "which rule sets the Faculty share" must resolve to exactly one (ambiguity there is a config error, not a plural outcome).

**`computeRevenueDistribution` (`src/services/revenue-allocation.service.ts`) is the formula itself, pure and unit-tested in isolation** — no DB, no I/O: `facultyShare` (fixed amount or `round(total × bps / 10000)`), `deductionsTotal` (sum of every resolved deduction), and if `facultyShare + deductionsTotal > totalAmountPesewas`, it throws `RevenueDistributionError` rather than clamping — clamping would silently misstate the ledger, and the spec's own two worked examples only make sense if the same fixed Faculty share can be valid against one payment amount and invalid against a smaller one. `departmentShare` is only ever computed once that check has passed, so it is never negative by construction, not by a floor. `resolveApplicableRevenueRule` and the new `resolveApplicableDeductions` both extend Phase 9/11's specificity-ranked resolver shape from 2 scope dimensions to the full 5.

**A misconfigured revenue rule can never corrupt a genuinely successful payment — this discipline now covers a new failure mode, not just races.** Phase 11 already made sure a race between webhook deliveries couldn't double-allocate; this phase adds "the configuration itself might reject the payment's amount" as a second reason allocation can fail, and treats it exactly the same way: `allocateRevenueForPayment` catches `RevenueDistributionError` internally, records an audit-log entry (`payment.allocation_failed`, with the computed reason and the rule that rejected it) and returns having created nothing — no `RevenueAllocation`, no wallet credit. `recordPaymentOutcome` (`payment.service.ts`) additionally wraps the whole call in a try/catch as a last-resort backstop. The only visible symptom on a payment that fails allocation this way is an empty "Revenue allocation" section on its admin detail page (Phase 12, unmodified) plus that audit-log row — no new UI surface invented for it, reusing what already existed.

**Proactive validation at configuration time is a second, best-effort line of defense, not the real guarantee.** Creating or editing a `FIXED`-mode `RevenueAllocationRule` or `RevenueDeduction` looks up currently-Active `DuesConfiguration` rows matching the rule's own *pinned* scope fields only (a wildcard field doesn't narrow the check) and rejects the save if the fixed amount, plus already-approved deductions in that scope, would exceed any matching configuration's amount. This catches an obviously broken configuration immediately in the admin UI instead of waiting for a real payment to fail — but it's necessarily incomplete (a dues configuration created *after* the rule can still be smaller than the rule's fixed share), which is exactly why the runtime check in `computeRevenueDistribution` is the one that actually matters and is exercised on every payment regardless.

**New capability `revenue:configure`** (`can.ts`), `ORG_ADMIN`-scoped, identical shape to `dues:configure`. `revenue-rule.service.ts` (new) holds rule CRUD; deduction CRUD (`create`/`update`/`list`/status-transition) was folded into `revenue-allocation.service.ts` itself rather than a separate file, since deductions are conceptually inseparable from the allocation formula they feed. Both new admin screens (`/admin/revenue-rules`, `/admin/revenue-deductions`) reuse `EditDialog` (Phase 7/12) rather than a bespoke wizard like Dues Configuration's — the field count (name, five scope selects, a share-type toggle, one amount/percentage input) doesn't need a multi-page review step. `EditDialog` gained a `size?: "sm" | "lg"` prop for this (existing call sites are unaffected, defaulting to the original `max-w-sm`) since six form fields need more room than the component's original single-column forms. A new "Revenue Distribution" nav section sits alongside Financial, data-driven through `nav-config.ts`'s existing `NavSection`/`getNavSections` shape — no changes needed in `nav-content.tsx`, which already renders sections generically from data.

**A real Mongoose gotcha surfaced during live verification, distinct from every prior phase's**: `next dev`'s Turbopack process had been running continuously since earlier phases, and Mongoose registers each model as a `mongoose.models[name]` singleton on first load — a source-file edit to an *existing* model's schema (as opposed to a brand-new model like `RevenueDeduction`) doesn't take effect in that already-running process, because `models.RevenueAllocationRule ?? model(...)` short-circuits on the stale cached model forever, even after Fast Refresh recompiles the module. The first live-verification pass genuinely failed against the *old* `splits`-based validator as a result ("Revenue split percentages must sum to 10000 basis points"), despite `tsc`, `lint`, and the pure-function unit script all being clean. Confirmed with the user before acting (this app's dev server is the user's own, per the standing rule from Phase 10/12 never to disrupt it unilaterally), then restarted the process — not a build, not touching `.next` — after which the same test passed cleanly. Worth remembering for any future phase that edits an *existing* model's schema shape while a long-lived dev server is attached.

**Verified**: a standalone script exercising `computeRevenueDistribution` directly against the spec's two worked examples (GH₵100 → 20/80, GH₵75 → 20/55), a payment too small for its fixed Faculty share (rejected, not clamped), a deduction stacked on a fixed rule (including the exact zero-department-share boundary, which is legitimate and not rejected), and a percentage-mode rule with a percentage deduction (rounding checked). Live, end to end as the seeded Org Admin: an obviously-too-large fixed Faculty share rejected inline against an existing dues configuration at rule-creation time; a valid rule saved and appearing in the table; a deduction created in `DRAFT` and transitioned to `APPROVED`; a real payment through the sandbox flow whose amount couldn't cover its rule's fixed Faculty share completing as `SUCCESSFUL` with a receipt, showing no Revenue Allocation section on its admin detail page, and producing a `payment.allocation_failed` audit-log row with the exact rejection reason; a second real payment correctly splitting Faculty GH₵20 / Department GH₵125 (GH₵150 − GH₵20 − the GH₵5 approved deduction) with both wallet balances crediting by the exact allocated amounts. All test payments, wallet credits, rules, deductions, and the extra dues configuration were cleaned up afterward. `tsc --noEmit` and `npm run lint` both clean.

## Phase 14: Financial Ledger

`RevenueAllocation` (Phase 1 schema, first wired in Phase 11, reused as-is by Phase 13) had been **two rows per payment** — one per beneficiary, `{beneficiaryType, beneficiaryId, amountPesewas}` — with no student/scope snapshot and no status at all. Phase 14's "Allocation record" is explicitly **one record per payment** carrying both shares as named fields plus a full context snapshot (student index number, faculty, department, category, level, payment period) and a `status` lifecycle (`ALLOCATED`/`REVERSED`/`ADJUSTED`) — a schema redesign, the same kind of wholesale replacement Phase 8/9/13 have each done when a phase's requirements didn't fit the prior shape.

**"Immutable" combined with a mutable `status` only makes sense read the same way `Payment.status` already works**: financial *facts* are set once and never rewritten; `status` is the one field that transitions. `ALLOCATED → REVERSED` already existed in spirit (a refund debited wallets without ever marking the allocation rows) and just needed the status write added. `ALLOCATED → ADJUSTED` is genuinely new and is **append-only, not in-place editing**: correcting a misallocated entry flips the original row's status to `ADJUSTED` and leaves every one of its numbers exactly as originally recorded, forever; a *new* row is created with the corrected shares, `status: "ALLOCATED"`, linked back via `adjustsEntryId`. Nothing is ever hidden or overwritten — the full history is queryable, which is what makes "trace every balance back to individual student payments" still true after a correction, not just before one.

**Data model** (`src/models/RevenueAllocation.ts`, redesigned): `studentIndexNumber`, `facultyId`/`facultyName`, `departmentId`/`departmentName`, `studentCategoryId`/`studentCategoryName`, `academicLevelId`/`academicLevelName`, `paymentPeriodId`/`paymentPeriodName`, `totalAmountPesewas`, `facultyShareAmountPesewas`, `departmentShareAmountPesewas`, `deductionsTotalPesewas`, `ruleId`/`ruleNameSnapshot`, `status`, `isCorrection`, `adjustsEntryId?`, `adjustmentReason?`. Every name comes free from data already on hand — `Payment.studentSnapshot` (Phase 1/10) already carries the four `*Name` fields alongside their ids — except `paymentPeriodName`, which needs one small `PaymentPeriod.findById` inside `allocateRevenueForPayment`, mirroring the existing `Organization.findById` lookup `recordPaymentOutcome` already does for the receipt number.

**The old unique index doesn't translate, and MongoDB partial indexes turned out to only support a narrow operator set.** The natural index for "at most one *original* row per payment, unlimited corrections" is a partial unique index on `{paymentId}` filtered to non-correction rows — but a `partialFilterExpression: {adjustsEntryId: {$exists: false}}` **fails at index-creation time** ("Expression not supported in partial index: $not") because MongoDB partial indexes support only equality, `$exists: true` (not `false`), comparison operators, `$type`, and top-level `$and` — `$exists: false` compiles internally to an unsupported `$not`. Fixed by adding a dedicated `isCorrection: boolean` field (default `false`) purely to drive the index via a supported equality condition — `partialFilterExpression: {isCorrection: false}` — the same partial-index pattern `PaymentPeriod.ts` already uses for "at most one Active period per org," just expressed through a field built for the purpose instead of an existence check. A second, real migration step was required beyond just changing the schema: the actual MongoDB collection still had Phase 11's old `{paymentId, beneficiaryType, beneficiaryId}` unique index physically present (Mongoose's `autoIndex` creates indexes newly declared in a schema but never drops ones that disappear from it), which caused duplicate-key errors on a second insert per payment even after the code was correct — a one-time `RevenueAllocation.syncIndexes()` was needed to drop it.

**`allocateRevenueForPayment` and `reverseRevenueAllocationsForPayment` (`src/services/revenue-allocation.service.ts`), reworked.** Allocation now creates one row instead of two; both wallet credits (Faculty then Department) source their `WalletTransaction` from that single row's `_id` — safe under the existing `{walletType, walletId, sourceType, sourceId}` unique index because `walletType` differs between the two calls even though `sourceId` is shared. Reversal's signature simplified from taking a hand-assembled partial `PaymentForAllocation` object to just `(paymentId, refundId)` — it finds whichever entry currently has `status: "ALLOCATED"` for that payment (the original, or its latest correction if one exists), debits both wallets by *that entry's own* stored shares, and flips its status via `findOneAndUpdate({..., status: "ALLOCATED"}, {$set: {status: "REVERSED"}})`, the same atomic-guard idempotency shape used everywhere else in this app — a second reversal call is a proven no-op, not a double debit.

**New `adjustLedgerEntry`, gated by a new `ledger:adjust` capability** (`ORG_ADMIN`, same shape as `revenue:configure`). Takes only a corrected Faculty share — the Department share is always *derived* (`total − facultyShare − deductionsTotalPesewas`, the same formula shape `computeRevenueDistribution` uses in Phase 13), never typed directly, so "never allow a negative department allocation" holds for manual corrections exactly as it does for automatic ones. Rejects adjusting anything that isn't currently `ALLOCATED` (a `REVERSED` payment's money already went back to the student; an already-`ADJUSTED` row has already been superseded — adjust the *current* entry, which is the correction, not the original). Wallet correction applies only the **delta** (`newAmount − oldAmount`, credited or debited depending on sign) via the existing `creditWallet`/`debitWallet`, sourced from the *new* row's own id with `sourceType: "ADJUSTMENT"` — a value that has sat unused in `WalletTransactionSourceType` since Phase 1, finally used for its intended purpose. `deductionsTotalPesewas` is always carried over unchanged from the original entry; correcting deductions is a `RevenueDeduction` configuration change (Phase 13), not a ledger adjustment.

**New `/admin/ledger`**, a server-driven list page following Payment Records' exact pattern (`<form method="get">`, DB-level filter + pagination via new `listLedgerEntries`, gated by the existing `payment:view` capability — Phase 12 never introduced a new capability per reporting screen, and the ledger is more of that same surface). `Pager` (`admin/payments/pager.tsx`) gained a `basePath` prop instead of a second near-duplicate component; its one existing call site now passes `basePath="/admin/payments"` explicitly. Each row links to `/admin/payments/[paymentId]` — the literal "trace every balance back to individual student payments" — and, only on `ALLOCATED` rows, an "Adjust" action (`EditDialog`, `size="lg"`, read-only current shares for context, one editable Faculty-share input, a required reason `Textarea`). Rows created by a correction show "Adjusts an earlier entry"; superseded rows show "Superseded" — nothing hidden, matching the append-only design. The Payment Details page's existing "Revenue allocation" section (Phase 12) was adapted from an array of beneficiary rows to the single current entry plus its status badge (new `LedgerStatusBadge`, `src/components/finance/`, mirroring `PaymentStatusBadge`'s shape).

**The Phase 13 lesson about `next dev` caching Mongoose models as process singletons repeated exactly** — redesigning an *existing* model's schema again meant the already-running dev server needed a restart before live verification could reflect it, confirmed with the user first, same as last time.

**Verified**: a standalone DB-level script exercising the partial unique index directly (a second non-correction row for the same payment rejected; a correction row with `isCorrection: true` not rejected), `adjustLedgerEntry`'s validation (a Faculty share large enough to force a negative Department share rejected; the original entry provably untouched afterward; re-adjusting an already-`ADJUSTED` entry rejected), the exact wallet delta math for both a credit-direction and debit-direction adjustment, and `reverseRevenueAllocationsForPayment`'s idempotency (a second call is a no-op). Live, end to end as the seeded Org Admin: a real sandbox payment producing exactly one `ALLOCATED` ledger row with the correct snapshot and Faculty/Department split, traceable from the ledger list to its exact payment; adjusting that entry's Faculty share and confirming the original flips to `Adjusted` with its original numbers intact, a new `Allocated` row appears with the corrected, formula-derived split, and both wallets reflect the exact delta (confirmed both in the UI and by direct database query); a second payment refunded through the existing Phase 12 `RefundAction` and its ledger entry correctly flipping to `Reversed`. All test payments, ledger entries, wallet transactions, wallet balances, and the seeded test rule were cleaned up afterward. `tsc --noEmit` and `npm run lint` both clean.

## Phase 15: Faculty Financial Dashboard

`/faculty/[facultyId]/page.tsx` had been a deliberate Phase 0/3 placeholder — its own comment said so — and `resolveHomePath` already routed `FACULTY_DEAN`/`FACULTY_PRESIDENT`/`FACULTY_TREASURER` there after login, so this phase filled in the page these three roles already land on rather than inventing a new route. Phase 14's ledger turned out to already carry exactly the five filter dimensions this phase asks for (`facultyId`, `departmentId`, `studentCategoryId`, `academicLevelId`, `paymentPeriodId`, plus `createdAt`) on every entry, so no new schema was needed — only new read queries against data that already existed.

**Two metric groups, because they have genuinely different scope.** "Total dues collected," "Faculty share earned," and "Successful payments" are per-payment facts, sliceable by the five requested filters. "Available balance," "Faculty share withdrawn," and the three withdrawal-status metrics are wallet-level facts — a wallet has one running balance, not a balance-per-category — so the dashboard presents them as a second, explicitly unfiltered group rather than forcing every filter onto every tile where it wouldn't mean anything.

**`getFacultyDashboardMetrics` (`src/services/dashboard.service.ts`, extended) sources "Total dues collected" and "Faculty share earned" from two independent queries, not one** — a `Payment` match for the former, a `RevenueAllocation` match (`status: {$ne: "ADJUSTED"}`, the same "currently active entry" pattern Phase 14 established) for the latter. This is deliberate: a payment whose revenue allocation failed outright (Phase 13's `RevenueDistributionError` path, no ledger row created) still correctly counts toward dues collected, while correctly contributing nothing to Faculty share earned — collapsing these into one query would either under-count collections or fabricate a share that was never actually allocated.

**A real bug, caught during live verification, not by `tsc`/`lint`**: `sumField()` (the aggregation helper already in this file since Phase 4, `model.aggregate([{$match}, {$group}])`) silently returned zero for every id-scoped filter. `.find()`/`.countDocuments()` auto-cast a plain string to `ObjectId` against a schema-typed field; `.aggregate()`'s `$match` stage does not — the same reason `payment.service.ts#getOrgTransactionVolumeTrend` already wraps `organizationId` in `new Types.ObjectId(...)` for its own aggregate, a precedent this phase's own match-building code initially missed. Fixed by explicitly casting every id-shaped filter value (`organizationId`, `facultyId`, and each optional scope filter) to `Types.ObjectId` before either `.countDocuments()` or `sumField()` sees it — one match object, correct for both call shapes. Caught because "Faculty share earned" and "Total dues collected" both rendered `GHS 0.00` against two real seeded payments while "Successful payments" (a `.countDocuments()`-only metric) correctly showed `2` — the split between the two call styles was the tell.

**Withdrawal request/approval, not release, is in scope.** `withdrawal:request`, `withdrawal:approve`, and `funds:release` have existed as capability stubs since Phase 5/11 with zero services or UI ever built against them — `WithdrawalRequest`/`WithdrawalApproval`/`WithdrawalSettlement` were real, unused schema. Without some way to create a `WithdrawalRequest`, three of this phase's eight required metrics would always read zero — not a mock, but not a meaningfully verified display either. Since this phase's own named roles are exactly the two actors who request and approve, `createWithdrawalRequest`/`decideWithdrawalRequest` (`dashboard.service.ts`) build that minimal loop: Treasurer requests (rejected server-side, in `createWithdrawalRequest`, if the amount exceeds the wallet's `balancePesewas` — the withdrawal-side restatement of "never allow a negative allocation"), Dean approves or rejects (atomic `findOneAndUpdate({..., status: "PENDING"})`, the same idempotency shape used everywhere in this app). Approval never moves the wallet balance — only an actual settlement would, and `funds:release` (Org Admin's side of the lifecycle) stays explicitly out of scope, the same way Phase 11 shipped `refundPayment()` with no UI and Phase 12 gave it one specifically when payment administration needed it. "Released withdrawals" correctly, honestly reads zero until a future phase builds that surface.

**The withdrawal amount field's own `max` attribute (the wallet's available balance) blocks an over-limit submission natively in the browser** — a real UX win (no wasted round trip) that also meant live verification of the *server-side* guard needed a second, direct path: a standalone script calling `createWithdrawalRequest` directly with an amount no UI `max` could gate, confirming the same `FacultyDashboardError` the UI's honest-but-unreachable-from-the-browser path exists to catch. Both were verified — the client constraint and the server invariant beneath it — rather than assuming the visible one implied the other.

**UI**: `page.tsx` reuses `StatTile` (Phase 4) and the GET-based `<form method="get">` filter pattern (Phase 12's Payment Records) unchanged. Department, academic level, student category, and payment period options for the filter dropdowns are fetched with plain, direct Mongoose queries inside `getFacultyDashboardMetrics` itself, not the existing `listDepartments`/`listAcademicLevels`/`listStudentCategories`/`listPaymentPeriods` functions — those all assert `organization:administer` (Org Admin/Super Admin only) and would reject a Faculty-role actor outright; the new `faculty-dashboard:view` capability (`can.ts`, layering an explicit Dean/President/Treasurer role check on the existing `inFaculty()` scope helper) is the one and only gate for this page's reads. A small withdrawal-requests table shows status badges (`PENDING`/`APPROVED`/`REJECTED` styled directly; `SETTLED` labeled "Released" in the UI, matching the phase's own wording over the model's internal enum name) with a Treasurer-only "Request withdrawal" `EditDialog` and Dean-only Approve/Reject `ConfirmDialog` actions — a President sees the identical dashboard with neither action button, matching the phase's "these three roles" framing without conflating view access with write access.

**Verified**: `tsc --noEmit` and `npm run lint` clean. Live, end to end: two real sandbox payments processed into Faculty of Science, viewed as the seeded Dean — Total dues collected (GH₵300), Faculty share earned (GH₵60 from a fixed-amount rule), and Successful payments (2) all correct; a deliberately bogus academic-level filter correctly zeroed the Collection group while the always-current Wallet group stayed unchanged; the real department filter correctly left totals unaffected. A newly-created Faculty Treasurer test user requested a withdrawal within the available balance (correctly appeared as Pending with the right amount) and was blocked by the field's own `max` when attempting one far beyond it; the direct server-side call for the same over-limit case was independently confirmed rejected. The Dean approved the valid request — it moved to Approved, the available balance stayed unchanged (no settlement exists yet), and Released withdrawals correctly stayed at zero. All seeded payments, ledger entries, wallet balances, and the test revenue rule were cleaned up afterward.

## Phase 17: Faculty Executive Management

Two generic pieces already existed and were reused, not rebuilt: `role-assignment.service.ts` (`assignRole`/`revokeRoleAssignment`, Phase 5) already handled creating/revoking any org-scoped role including the three Faculty ones, and `user.service.ts` (`deactivateUser`/`reactivateUser`) already handled suspending a login account — reused directly, unchanged. What was missing was the *faculty-scoped, role-filtered management surface* — the same relationship `listOrgAdmins`/`assignOrgAdmin`/`revokeOrgAdmin` (Phase 5) already has to the generic service for Org Admins, now built for Faculty executives on the previously read-only "Executives" section of `/admin/faculties/[facultyId]`.

**"Activate/deactivate," "Change role," and "Remove executive" are three distinct actions, not two relabeled.** Remove is `revokeRoleAssignment` (loses the Faculty role; account and any future role assignment remain). Activate/deactivate is `deactivateUser`/`reactivateUser` (the login account itself is suspended entirely — identical to `/admin/users`'s existing behavior, reused as-is). Change role is new: rather than mutating the existing `UserRole` row in place — which would erase the fact that the person ever held the old role — `changeFacultyExecutiveRole` (`src/services/faculty-executive.service.ts`) revokes the old row and creates a new one for the same person, the same append-only "supersede, never overwrite" shape Phase 14 established for ledger corrections. This is also what makes **"View executive history" free**: every `UserRole` row ever created for a faculty's three roles, active or revoked, *is* the history — `listFacultyExecutiveHistory` just queries all of them instead of only `isActive: true`, no new schema or audit-log parsing required, the same reasoning that made Phase 14's `RevenueAllocation` rows themselves the ledger rather than a separate trail.

**"The Faculty Dean must act as the superior approval authority" was already true in `can.ts`** (`withdrawal:approve` already checked `role === FACULTY_DEAN`, never President or Treasurer) but nothing stopped an Org Admin from assigning *two* Deans to one faculty, which would make "the" authority ambiguous. Closed with one new partial unique index on `UserRole`: `{organizationId, facultyId}` unique, filtered to `{isActive: true, roleKey: "FACULTY_DEAN"}` — both plain equality conditions, the kind MongoDB partial indexes support directly (confirmed against the `$exists`-isn't-supported lesson Phase 14 already ran into). `createFacultyExecutive`/`changeFacultyExecutiveRole` both pre-check for an existing active Dean before ever reaching the database, so the index is a backstop for a genuine race, not the primary UX — verified live against both a freshly-seeded test faculty and a real, pre-existing faculty (Faculty of Science, already carrying a Dean from Phase 5 testing), confirming the constraint isn't something that only holds for test-seeded data. President and Treasurer were deliberately left unconstrained — neither gates an exclusive capability the way Dean gates `withdrawal:approve`, so multiple active holders isn't ambiguous the same way.

**No faculty picker in the create-executive UI** — `createFacultyExecutive` always assigns to the faculty the admin is already viewing; "assign faculty" is satisfied by page context rather than a cross-faculty transfer feature nothing in the spec asked for. `getFacultyDetails` (`faculty.service.ts`) had its old bare `executives` field removed now that `listFacultyExecutives`/`listFacultyExecutiveHistory` supersede it entirely.

**The dev-server-model-caching lesson (Phase 13/14/15) applied a fourth time** — this phase only added an *index* to `UserRole`, no field/interface change, but the same Mongoose-singleton caching still applied (indexes are registered once per process too), so a restart was still needed before live verification could reflect the new constraint. **`DEAN_APPROVED` is a real, audited status that's never a resting one.** The documented workflow has no manual "escalate to Super Admin" step for anyone to take, so the Dean/HOD's `APPROVED` decision (`decideFirstStageApproval`) performs two sequential, atomic, separately-audited writes in one service call: `PENDING_DEAN_APPROVAL → DEAN_APPROVED` immediately followed by `DEAN_APPROVED → PENDING_SUPER_ADMIN_APPROVAL`. `SUPER_ADMIN_APPROVED`, by contrast, does rest — approving and releasing funds are legitimately separate actions (the spec draws them as two distinct boxes), so nothing auto-chains after Super Admin approval; `releaseWithdrawalFunds` is its own explicit step.

**An explicit `ALLOWED_TRANSITIONS` map is checked before every status-changing write** (`assertTransition`, `withdrawal.service.ts`) — the literal backend answer to "the documented workflow must be enforced in the backend, not merely represented visually." Fund release is itself ledger-first and atomic-guard-ordered, same as every money-moving write since Phase 14: the status flips to `RELEASED` via `findOneAndUpdate({_id, status: "SUPER_ADMIN_APPROVED"})` *before* `debitWallet` runs, so a crash between the two leaves a released-but-not-yet-debited request rather than a debited-but-not-released one — recoverable, never double-spent.

**"Do not allow withdrawals greater than available balance" is enforced against simultaneous in-flight requests, not just the raw wallet figure.** `getAvailableBalance` subtracts every *other* request currently `PENDING_DEAN_APPROVAL`/`RETURNED_FOR_CORRECTION`/`PENDING_SUPER_ADMIN_APPROVAL`/`SUPER_ADMIN_APPROVED` (submitted but not yet released or terminally closed) from the wallet's balance, and both draft-creation and submit re-check it — a request that fit when drafted can still be correctly rejected at submit time if another request consumed the balance first in the meantime.

## Phase 22: Wallet & Settlement System

**Most of "never simply update a balance without recording a corresponding wallet transaction" was already true before this phase** — `creditWallet`/`debitWallet` (`src/lib/wallets/ledger.ts`, Phase 19) have always written a `WalletTransaction` row *before* `$inc`-ing the wallet, and "approval ≠ release" already held structurally (only `releaseWithdrawalFunds` ever touched `balancePesewas`). What this phase actually adds, read literally against the six required transaction types and the existing code:

**Two transaction types didn't exist, and one was misnamed.** `WalletTransactionSourceType` (`shared/types.ts`) gained `WITHDRAWAL_HOLD` and `CORRECTION`; `WITHDRAWAL_SETTLEMENT` was renamed `WITHDRAWAL_RELEASE` to match the phase's own vocabulary (three occurrences, a cheap and safe rename). `WalletDirection` gained a third value, `HOLD` — deliberately not reusing `DEBIT`, since a hold never actually moves `balancePesewas` and reusing `DEBIT` would corrupt any credit-minus-debit reconciliation of the real balance.

**"Withdrawal hold" is now a real ledger event, not just a live computation.** Before this phase, a submitted request's reservation was only ever computed on the fly (`getAvailableBalance`'s aggregate over `WithdrawalRequest` — still exactly how it's enforced, unchanged). Nothing recorded that the hold *happened*. `submitWithdrawalRequest` now calls a new `recordWalletHold()` (`ledger.ts`) right after its atomic guard succeeds — one insertion point covers both Faculty's explicit Submit and Department's one-step `createAndSubmitWithdrawalRequest`, which calls it internally. `recordWalletHold` writes a `direction: "HOLD"` transaction with `balanceAfterPesewas` equal to the wallet's *current, unchanged* balance and, critically, **never calls `$inc` on the wallet at all** — the literal code-level enforcement of "approval does NOT equal fund release." A resubmission after Return-for-correction re-triggers the same call; the existing unique `{walletType, walletId, sourceType, sourceId}` index makes it a silent no-op (same duplicate-key handling `creditWallet`/`debitWallet` already had) — an accepted simplification, since the hold is an audit record of *when encumbrance began*, not what actually enforces the balance check.

**A new `computeLedgerBalance()` is the literal proof that "wallet balances must be calculated from financial transactions."** It sums `CREDIT − DEBIT` over a wallet's `WalletTransaction` rows (excluding `HOLD`, which never affected the real balance) and — verified directly — matches `wallet.balancePesewas` after every operation: a revenue credit, a withdrawal hold (unchanged), Dean approval (unchanged), Super Admin approval (unchanged), a release (drops by exactly the released amount), and a correction (moves by exactly its delta). `balancePesewas` was never an independently-trusted field; this makes that provable, not just asserted.

**"Adjustment" and "Correction" were conflated — now they're not.** The only wallet-touching caller of `ADJUSTMENT` was `adjustLedgerEntry` (`revenue-allocation.service.ts`), whose own doc comment says "Corrects a misallocated entry." That's a **Correction**, not a manual, standalone **Adjustment** — nothing in this codebase does the latter today, and Phase 22 doesn't ask for a new feature to do it either, only for the transaction type to exist in the taxonomy. `adjustLedgerEntry`'s four `creditWallet`/`debitWallet` calls are now tagged `CORRECTION`. The "Adjust allocation" UI label (`admin/ledger/adjust-ledger-entry-dialog.tsx`) is unchanged — a fine name for the feature; only the ledger tag underneath it changed to be semantically accurate. `ADJUSTMENT` stays defined in the enum, reserved for a genuine future manual-balance-adjustment feature — the same way `WITHDRAWAL_SETTLEMENT` (now `WITHDRAWAL_RELEASE`) sat dormant for four phases before Phase 19 wired it up.

**No `WalletTransaction` had ever been visible in any UI before this phase** (confirmed by grep) — the Faculty/Department dashboards showed aggregate stat tiles but never the underlying ledger, making the "Settlement System" invisible from a user's perspective. A new `src/services/wallet.service.ts#listWalletTransactions` (gated by the same `faculty-dashboard:view`/`department-dashboard:view` capabilities everything else on that dashboard already uses) and a new shared `wallet-transactions-table.tsx` give both dashboards a "Wallet transactions" section — every hold, release, allocation, reversal, and correction, newest first, with a `HOLD` row's "Balance after" rendered as `—` (it never moved) to keep the distinction visible rather than implied.

**Verified**: `tsc --noEmit` and `npm run lint` clean. This renames/extends the `WalletTransaction` model's enums — dev-server restart needed, confirmed with the user first (eighth time this session). A standalone script (`scripts/verify-phase22-ledger.ts`) proved the full invariant chain directly against the ledger: revenue credit → `computeLedgerBalance` matches; submit → `WITHDRAWAL_HOLD`/`HOLD` recorded, balance untouched, `computeLedgerBalance` still matches; Dean approval → balance untouched; Super Admin approval → balance untouched; release → `WITHDRAWAL_RELEASE`/`DEBIT` recorded, balance drops by exactly the released amount, `computeLedgerBalance` matches; a separately-rejected request's hold transaction remains in the ledger, balance unaffected; `adjustLedgerEntry` → `CORRECTION`, not `ADJUSTMENT`, balance moves by exactly the delta. Verified nothing reads a `Student` document assuming they're non-null before loosening them — the live payment path never touches `Student` at all.

**A new dependency, installed carefully.** No CSV/Excel parser existed. `xlsx` (SheetJS) parses both formats via one API (`XLSX.read(buffer, {type: "buffer"})`), but the npm-registry build carries two unfixed high-severity CVEs (prototype pollution, ReDoS) — directly relevant since this feature's entire job is parsing untrusted uploaded files. Installed SheetJS's own patched build from their CDN tarball (`https://cdn.sheetjs.com/xlsx-latest/xlsx-latest.tgz`) instead of the vulnerable npm version — `npm audit` reports zero vulnerabilities.

**"Index-number-based matching"** = each valid row is `Student.findOneAndUpdate({organizationId, indexNumber}, {$set: <only this row's non-empty fields>}, {upsert: true})` — creates or merges, keyed on the model's existing unique index, and a blank optional cell never erases a value a previous upload already set. **"Preserve the original uploaded file"** = `StudentListUpload` gained `originalFileData` (a `Buffer`), `originalFileMimeType`, and `originalFileSizeBytes` — stored inline (safely under MongoDB's 16MB document cap once the 5MB ceiling is enforced), served back byte-for-byte via a new authenticated route handler rather than any external storage dependency.

**The validation pipeline is genuinely two-tiered.** File-level failures (wrong extension, oversized, unparseable, missing the "Index Number" or "Full Name" column) reject the whole upload before any row is touched — for the unparseable/missing-column case a `FAILED` `StudentListUpload` is still recorded (with the file preserved) so the history shows *why*; for the format/size checks, nothing is stored at all, since a file that's already-obviously-not-a-submission (wrong type, absurdly large) was never really accepted. Row-level validation then runs per row: missing index number, missing full name, an index number repeated earlier in *this same file* (`DUPLICATE`, distinct from re-uploading a corrected file across separate uploads, which is the intended update path), and an optional Faculty/Department/Academic Level/Student Category cell that's non-empty but doesn't resolve against the org's own records (matched by name *or* code) — each gets its own specific `errorReason`, and the upload itself still completes (`COMPLETED`, not `FAILED`) since partial success is the normal case for a real-world roster file.
